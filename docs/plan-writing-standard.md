# 计划文档规范

生效日期：2026-09-27。适用于本仓库以后由计划模式或其他 harness 产出的实施方案。当前开发目标只有微信小游戏；历史资料中的双平台要求不自动延续。

## 什么时候落盘

- 普通讨论和短计划留在对话中。用户要交给其他执行者、要求保存，或工作跨会话时，才创建持久方案。
- 每个主题只有一份当前方案：新文档的文件名尽量使用简短、清晰的中文主题名，例如 `docs/plans/召唤与元宝经济.md`。目录名、扩展名和代码、脚本或工具要求的标识可保留英文；现有文档不因本规则重命名。不要用 `v1-final-new` 连续复制文件；方案改变时修改原文件，并在文末记简短变更记录。
- 相关原型、截图和提示词放 `docs/prototypes/<主题>/`；实际运行资源进入 `assets/resources/`。研究记录与验收证据可放 `docs/research/`、`docs/reviews/`，并由方案链接，不复制整篇内容。
- 旧文档集中在 `docs/archive/2026-09/`，仅供追溯。不要拿归档稿直接作为当前任务指令；先对照 `AGENTS.md`、`session_context.md` 和现行源码。

## 状态与权威性

每份方案开头必须写：`状态`、`适用平台`、`负责人/维护者`、`更新日期`、`代码基线`、`决定来源`。状态只用以下四种：

| 状态 | 含义 |
| --- | --- |
| 草案 | 供讨论；数值和取舍尚未成为产品决定。 |
| 已确认 | 用户明确选定方向或已发出实现指令；写清确认范围与来源。 |
| 实施中 | 已开始开发，列出真实已完成和待完成项。 |
| 已验收 | 有可复核的测试或设备证据，写明覆盖范围；未测部分保持未测。 |

废止的方案移到 `docs/archive/<年月>/`，当前索引写明替代文档。状态是记录事实，不是额外的开工审批：用户已经要求实施时直接工作，不因为文档还写“草案”而重复索取许可。不同执行者不得把建议、已实施、已验收混写为同一结论。

## 方案正文最低结构

1. **目标与玩家体验**：触发场景、玩家操作和期望结果，尽量给出一个具体例子。
2. **已核实的现状**：关联源码、当前数值与问题；把推断、竞品观察和待确认项单独标注。旧方案不等于现行代码。
3. **范围与不做项**：本次影响的页面、规则、存档、微信构建；列出明确不做的扩展。
4. **设计规则与数值**：玩法流程、边界条件、计算口径、可配置项；关键数字说明如何得出及其对玩家节奏的影响。
5. **实施顺序**：按可独立验证的步骤列出源文件或模块、迁移和兼容策略、交接边界。不要把生成文件当源码。
6. **验收标准**：可观察的正常路径、失败路径、旧存档、边界时间及对应验证方式；区分自动检查、开发者工具、真机。
7. **风险与开放问题**：尚无数据支持的假设、需要用户取舍的决策，以及上线前要测的指标。
8. **变更记录**：只记影响方案结论的修改和日期，不粘贴聊天记录。

文档只写完成一项任务所需的细节，不复写 `AGENTS.md` 或整份 `session_context.md`。路径用仓库相对路径；引用其他资料时用可点击的相对链接。重要结论以当前源文件和实际验证为准。

## 入库与维护

- 新方案建立后同步更新 `docs/README.md` 的“当前方案”索引；验收完成或归档时同步更新索引与状态。
- 每次任务按 `AGENTS.md` 追加 `session_context.md` 交接并提交。文档改动只做链接、内容和格式检查；没有改游戏代码时不为文档启动 Cocos 构建。
- 执行者接手方案前，先核对最新代码与用户决定；发现冲突时在方案中写明差异，再据当前授权处理，不静默复用旧指令。
